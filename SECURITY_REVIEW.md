# SECURITY_REVIEW.md — red-team-style review

Дата: 2026-09-13. Проведено как код-ревью с точки зрения атакующего
(без доступа к живому продакшн-серверу — только статический анализ
кода в этом репозитории). Оценивается: клиентское приложение (Vite/TS,
localStorage), Supabase-слой (auth + RLS), `sandbox-server/` (реальный
Docker-контейнер на настоящем сервере — единственная часть проекта с
реальным серверным риском).

## Итог

Общая осанка приличная для проекта такого масштаба: анон-ключ Supabase
используется по назначению (защита через RLS, не через секретность),
XSS-векторы через `innerHTML`-шаблонизацию последовательно закрыты
`esc()` там, где рендерится пользовательский текст (username на
лидерборде), контейнер капстоуна захардкожен разумно строго (no
network, cap-drop all, read-only, лимиты ресурсов). Найдено **одна
конкретная эксплуатируемая ошибка** (bypass проверки Origin) и
**две архитектурные проблемы среднего риска**, плюс несколько заметок.
Ничего из найденного не является критическим (нет RCE «из коробки», нет
утечки секретов), но #1 и #2 стоит закрыть до того, как на сервер
пустят реальный трафик недоверенных пользователей.

## Находки

### 1. [Medium] Обход allowlist по Origin в sandbox-server — эксплуатируемо

**Файл:** `sandbox-server/server.js`, функция `verifyClient`:

```js
verifyClient: ({ origin, req }, done) => {
  const ip = req.socket.remoteAddress || "?";
  if (ALLOWED_ORIGINS.length && origin && !ALLOWED_ORIGINS.includes(origin)) {
    log("warn", "origin rejected", { origin, ip });
    return done(false, 403, "origin not allowed");
  }
  ...
```

Условие `ALLOWED_ORIGINS.length && origin && !...` **пропускает**
проверку, если `origin` **отсутствует** (falsy) — а WebSocket-клиент,
не являющийся браузером (`wscat`, кастомный скрипт, curl с
`Upgrade: websocket`), может просто не отправлять заголовок `Origin`
вообще. В таком случае условие `origin &&` не выполняется, и весь блок
`if` пропускается — allowlist полностью обходится.

**Эксплуатация:** имея валидный Supabase JWT (получить который может
любой, кто зарегистрировался — регистрация открыта), атакующий
подключается к `wss://.../sandbox` напрямую (не из браузера, не с
разрешённого домена) и получает такой же контейнер, как обычный игрок.
Смысл проверки Origin («чужой сайт с украденным токеном не может гонять
песочницы за наш счёт», как написано в комментарии в начале файла)
полностью аннулируется для не-браузерных клиентов — а именно от них и
защищаются подобные проверки в реальности.

**Исправление:**
```js
if (ALLOWED_ORIGINS.length && (!origin || !ALLOWED_ORIGINS.includes(origin))) {
  return done(false, 403, "origin not allowed");
}
```
(отклонять и отсутствие Origin тоже, когда allowlist задан).

### 2. [Medium] Лидерборд принимает нефальсифицируемые на вид, но фактически клиентские данные

**Файлы:** `supabase_schema.sql` (`public_stats` RLS), `src/sync/cloud.ts` (`pushProfile`).

RLS на `public_stats` разрешает `insert`/`update` любому, где
`auth.uid() = id`, **без проверки значений** `xp`/`missions_done`/
`rank_name` относительно того, что реально пройдено на сервере. Курс
целиком выполняется в браузере — нет backend-функции, которая бы
пересчитывала XP независимо от клиента. Значит: авторизованный
пользователь может отправить прямой запрос к Supabase REST API (используя
свой собственный легитимный JWT — никакого обхода авторизации не
требуется) с произвольным `xp: 999999999`, обойдя весь клиентский код
игры, и это тут же появится в публичном лидерборде.

**Эксплуатация:** тривиальна для любого, кто откроет DevTools → Network
и один раз скопирует запрос `pushProfile`, поменяв значения.

**Оценка риска:** невысокая (это обучающая игра, не финансовая система),
но подрывает доверие к лидерборду как к социальному доказательству
прогресса — а именно в этом его единственная функция. Если лидерборд
важен продукту, это стоит закрыть.

**Исправление (варианты, не взаимоисключающие):**
- Supabase Edge Function / Postgres `trigger`/`check constraint`,
  которая пересчитывает `public_stats` из `profiles.state` на сервере,
  а не принимает значения от клиента напрямую (то есть `public_stats`
  становится производной, а не независимо записываемой таблицей).
- Хотя бы верхняя граница правдоподобия в `check`-constraint (например,
  `xp <= 5000` — по факту максимум за реально существующий контент) —
  не защита в полном смысле, но поднимает порог тривиальности.

### 3. [Low] Открытая регистрация без анти-абьюз мер → ресурсная нагрузка на sandbox-хост

`signUp()` (`src/sync/cloud.ts`) не имеет капчи/лимита на стороне
приложения (Supabase может иметь свои лимиты — не проверялось, это вне
этого репозитория). В сочетании с `sandbox-server/server.js`:
`MAX_CONCURRENT` (по умолчанию 5) — это лимит на **сервер**, не на
пользователя выше одной активной сессии; при этом `docker run`/`docker
rm` — не бесплатные операции. Скрипт, создающий N аккаунтов и
поочерёдно занимающий/освобождающий контейнеры, создаёт устойчивую
фоновую нагрузку на хост и/или блокирует доступ реальным игрокам
(`MAX_CONCURRENT` быстро исчерпывается). Rate-limit в `verifyClient` —
**по IP**, обходится тривиально ротацией IP/акка.

**Рекомендация:** капча на регистрации (Supabase поддерживает hCaptcha/
Turnstile из коробки), либо подтверждение email перед выдачей доступа к
sandbox, либо серверный rate-limit по `userId`, а не только по IP.

### 4. [Info] Неиспользуемая часть схемы БД — `comments` (решение за владельцем)

`supabase_schema.sql` описывает таблицу `comments` с RLS-политиками
(`select all`, `insert own`, `delete own`), но ни один файл в `src/ui/*`
её не читает и не пишет — фича, судя по всему, не была доведена до UI.
Не уязвимость сама по себе, но лишняя, никем не тестируемая
поверхность в реальной БД (RLS на ней не проверялась ни разу
интеграционно, так как ничего её не вызывает).

**Намеренно не удалено в этом раунде изменений**: если таблица уже
создана на живом проекте Supabase, в ней потенциально может быть
что-то записано — `drop table` необратим, и я не стану добавлять его в
`supabase_schema.sql` без явного отдельного подтверждения именно этого
шага. Решение за владельцем проекта:
- если данных в таблице нет и функция не нужна — выполнить вручную
  в Supabase SQL Editor: `drop table if exists public.comments cascade;`
- если функция нужна — написать экран в `src/ui/*` поверх уже готовых
  RLS-политик (сама схема для этого готова).

### 5. [Info] Целостность локального прогресса — принято как есть

Любой пользователь может через DevTools отредактировать
`localStorage["devops_terminal_rpg_v1"]` напрямую (выставить `xp`,
`jobs`, `done`, обнулить `deathPending`, обойти экзамен на выживание и
т.д.). Это **ожидаемо и приемлемо** для однопользовательской обучающей
игры без ставок — сам себе вредит только тот, кто это делает. Стало
только чуть более значимым с появлением публичного лидерборда (см. #2)
и облачной синхронизации, потому что подделанный локальный прогресс
может утечь в общедоступную витрину при следующем `pushProfile()`.
Отдельного действия не требует, если #2 закрыт правильно (пересчёт на
сервере снимает и эту проблему заодно).

## Что сделано правильно (стоит сохранить как есть)

- Анон/publishable ключ Supabase — единственный ключ в клиентском коде,
  никакого `service_role` ключа в репозитории не найдено (проверено
  `grep`); дизайн верный — секретность не требуется, всё держится на
  RLS.
- `esc()` (`src/ui/dom.ts`) последовательно применяется ко всем полям с
  пользовательским текстом, которые рендерятся через `innerHTML`
  (`r.username`, `r.rank_name` в `ui/leaderboard.ts`; все вопросы/тексты
  в диалогах интервью и экзамена на выживание — хотя это статичный
  контент из `data/*.ts`, не пользовательский ввод, `esc()` всё равно
  применён единообразно, что снижает риск при будущих изменениях).
  Сертификат (`ui/certificate.ts`) рисует имя через `canvas.fillText`,
  что по природе безопасно от HTML-инъекции.
- `sandbox-server/server.js` вызывает `docker` через `execFile` с
  массивом аргументов (не через shell-строку) — инъекция команд через
  параметры исключена.
- Хардненинг контейнера капстоуна разумен и превышает типичный уровень
  для подобных учебных песочниц: `--network none`, `--cap-drop ALL`,
  `--security-opt no-new-privileges`, `--read-only` + ограниченный
  tmpfs, non-root (`1000:1000`), лимиты memory/cpu/pids, `--ulimit`
  на nproc/nofile, автоматический таймаут и уничтожение по разрыву
  соединения.
- Аутентификация sandbox-сессии — сервер сам проверяет JWT у Supabase
  (`GET /auth/v1/user`), не доверяет клиентски-подписанным данным.

## Приоритет исправления (если согласовывается отдельно)

1. #1 (Origin bypass) — тривиально исправить, стоит сделать прежде,
   чем `sandbox-server` получит реальный внешний трафик.
2. #2 (лидерборд) — важно только если лидерборд как социальный
   элемент продукта имеет значение для пользователя; иначе можно
   оставить как принятый риск обучающей игры.
3. #3 (анти-абьюз регистрации) — стоит закрыть, если `sandbox-server`
   выкладывается публично на постоянной основе, а не для личного
   использования владельца.
4. #4, #5 — не требуют немедленных действий.
