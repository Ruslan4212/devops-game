## 1. Что это за проект

**Terminal Ops Academy** (репозиторий называется `devops-academy`,
внутриигровое имя раньше было «Pipeline: путь до Middle DevOps») —
браузерная обучающая игра, которая готовит человека с нуля до уровня
**Junior/Middle DevOps-инженера**, способного пройти реальное
техническое собеседование.

Формат: **симулятор терминала Linux в браузере** + пошаговые уроки
(«смотри → повтори → сделай → вопрос») + RPG-надстройка поверх учёбы
(деньги, здоровье, настроение, покупки, карьера, собеседования,
персонаж). Ничего не выполняется по-настоящему на компьютере игрока —
весь `bash`/`git`/`docker`/`kubectl`/`terraform`/`python3`/`zabbix_get`
и т.д. эмулируется в памяти JS (см. §4). Единственное исключение —
финальный капстоун, который даёт настоящий изолированный Linux-контейнер
на отдельном сервере (см. §7).

### Кому это адресовано

Пользователь (владелец проекта) сам проходит курс, чтобы устроиться
DevOps-инженером, и одновременно является «продюсером» игры — просит
расширять контент и механики так, чтобы это реально помогало готовиться
к собеседованиям, а не было игрой ради игры.

## 2. Сюжет и педагогическая идея

Сквозной сюжет (полностью описан в `src/data/careers.ts`, массив
`STORY`): игрок — случайный человек, к которому вечером обращается
знакомый с сайтом на одном сервере («Слушай, сайт лёг»). Через это
случайное происшествие игрок втягивается в профессию: сначала подработки,
потом первая официальная работа, потом сложные инциденты, потом его
самого начинают спрашивать, и в финале — оффер на Middle.

Курс разбит на **14 «актов»** (`src/lessons/act01.ts` … `act14.ts`),
каждый — отдельная область DevOps, изучаемая строго последовательно:

| Акт | Тема |
|----|------|
| 1 | Linux и терминал с нуля (файлы, права, процессы) |
| 2 | Сервисы и systemd, journalctl |
| 3 | Bash-скрипты, пайплайны, `test`/`[ ]`, `set -e` |
| 4 | Сети: curl, коды ответа, TCP/UDP, TLS, DNS |
| 5 | Git: ветки, merge, конфликты, теги, amend |
| 6 | Docker: образы, multi-stage, `-e`/`-v`, `rmi` |
| 7 | CI/CD: пайплайны, approval-gate, rollback |
| 8 | Terraform: plan/apply, drift, taint, state rm |
| 9 | Kubernetes: deployments, pods, scheduling |
| 10 | Дежурство (on-call), алерты, надёжность |
| 11 | Prometheus: PromQL, экспортёры, правила |
| 12 | Grafana: дашборды, панели, датасорсы |
| 13 | Zabbix: агент, item, триггеры, LLD |
| 14 | Python для DevOps: requests, argparse, subprocess, os.environ, retry |

Каждый акт: **~20 уроков** (все акты расширены до 18–21 урока в этой и
предыдущей больших сессиях; см. §9) + один **экзамен акта**
(`src/lessons/exams.ts`, id вида `"экз1"` … `"экз14"`, вопросы по
возрастанию сложности `d: 1..7`). Урок = маленький шаг, ошибиться
нельзя «фатально» — после N попыток показывается подсказка, затем
готовый ответ. Это осознанный дизайн: курс **не должен фрустрировать**,
кроме специально выделенных инцидентов и финального экзамена на
выживание (см. §6).

## 3. Технологический стек

- **Vite 5** + **TypeScript 5.6** (строгий режим), сборка в обычный
  multi-file бандл (`npm run build`) и в **single-file HTML**
  (`npm run build:single`, плагин `vite-plugin-singlefile` — весь JS/CSS
  инлайнится в один `index.html`, это то, что публикуется в `play/`).
- **Vanilla TypeScript DOM**, без React/Vue/любого фреймворка. Каждый
  «экран» (персонаж/жизнь/карьера/собеседование/…) — это функция в
  `src/ui/*.ts`, которая **целиком перезаписывает** `#modBody.innerHTML`
  строкой-шаблоном и вручную перепривязывает `onclick`. Общий модальный
  контейнер: `#modOv`/`#modBody` в `index.html`, класс `.hide` открывает/
  закрывает. Это единственный архитектурный паттерн UI в проекте —
  **придерживайся его**, не вноси React/компонентный подход частично.
- **Vitest 2** для тестов (`npm test`), **ESLint 9** (`npm run lint`),
  **Prettier 3** (`npm run format`). Все три должны быть чистыми перед
  коммитом.
- **Supabase** (Postgres + Auth) — необязательный облачный слой:
  синхронизация прогресса между устройствами и публичный лидерборд.
  Работает на **anon (publishable) ключе**, безопасность — через RLS-
  политики в `supabase_schema.sql`. Если не настроено — игра полностью
  работает на одном `localStorage` (`src/engine/progress.ts`, ключ
  `devops_terminal_rpg_v1`).
- **`@xterm/xterm`** — настоящий терминал (не эмуляция уроков) для
  капстоуна, подключается к отдельному Node.js-серверу
  (`sandbox-server/`, Express + `ws` + `node-pty` + Docker) через
  WebSocket с аутентификацией по Supabase JWT.

### Как запускать

```bash
npm install
npm run dev             # http://localhost:5173, живая пересборка
npm test                # 1000+ тестов, должны быть все зелёные
npm run typecheck && npm run lint && npm run format:check
npm run build:single     # собирает dist-single/index.html
cp dist-single/index.html play/index.html   # это и есть "продакшн" копия
```

## 4. Архитектура кода (где что лежит)

Три **независимых** слоя состояния — это важно понимать, чтобы не
перепутать, куда добавлять новое поле:

1. **`World`** (`src/engine/types.ts`, `src/engine/world.ts`) —
   состояние симулятора терминала ОДНОГО урока: файловая система
   (`vfs.ts`), процессы, git/docker/k8s/ci/terraform/prometheus/grafana/
   zabbix/python state. Живёт только пока открыт урок, не персистится
   между уроками напрямую (кроме прогресса done/xp). Команды —
   `src/commands/*.ts`, регистрируются через `def(name, fn)` из
   `src/commands/registry.ts`, подключаются side-effect импортами в
   `src/commands/index.ts`. Исполнение строки — `src/engine/shell.ts`
   (`execLine`/`execPipeline`, поддерживает `&&`/`||`, `|`, `>`/`>>`,
   позиционные аргументы скриптов, `set -e`, `exit N`).
2. **`Lesson`** (`src/engine/types.ts`) — модель одного урока: массив
   `steps` (`say`/`watch`/`type`/`do`/`quiz`), опциональный `setup(w)`.
   Все уроки собраны в `src/lessons/index.ts` из `act01..act14` +
   `exams.ts`. Проигрывание урока — `src/engine/lesson-run.ts`
   (`LessonRun`), используется и в реальном UI (`src/main.ts`), и в
   тестах (`tests/lessons.spec.ts` автоматически проходит **каждый**
   урок через `LessonRun.autoplay()` — это главный тест, доказывающий,
   что курс физически проходим).
3. **`Progress` / `Life`** (`src/engine/progress.ts`,
   `src/engine/life.ts`) — RPG-метасостояние, персистится в
   `localStorage` целиком одним JSON (`saveProgress`/`loadProgress`).
   `Progress` = `{ xp, done, cur, hints, jobs, life, capstone, strict,
   deathPending, deaths, ... }`. `Life` (вложен в `Progress.life`) =
   деньги, голод/здоровье/настроение, одежда/обувь/аксессуар, жильё,
   машина, техника, поездки, внешность (`look: Appearance`, из
   `src/data/avatar.ts`).

Дополнительно:
- **`src/data/*.ts`** — статические каталоги без логики: `shop.ts`
  (еда/одежда/жильё/машины/техника/поездки/аксессуары/уют),
  `careers.ts` (вакансии, поведенческие вопросы, сюжет,
  `ACT_TO_TOPIC`), `interview.ts` (849+ строк технических вопросов по
  10 темам), `avatar.ts` (SVG-генерация персонажа), `glossary.ts`
  (справочник команд), `capstone-tasks.ts`.
- **`src/missions/*`** — это **прежняя версия игры** (до перехода на
  формат «уроков»), сохранена для обратной совместимости и переноса
  старых сохранений (`src/sync/legacy-import.ts`,
  `src/lessons/legacy-adapter.ts`). Не расширяй её — новый контент идёт
  только в `src/lessons/actNN.ts`.
- **`src/sync/*`** — Supabase-аккаунт, облачное сохранение, слияние
  прогресса с двух устройств (`merge.ts`, побеждает версия с большим
  `totalEarned`/дальше пройденная), перенос легаси-сохранений.
- **`src/sandbox/*`** + **`sandbox-server/`** — капстоун на настоящем
  контейнере, см. §7.

### Тестовый паттерн (обязательно соблюдать при любом расширении)

При любом новом движковом механизме (новая команда, новое поведение
`shell.ts`, новая RPG-механика) — создаётся **отдельный** файл
`tests/<feature>-command.spec.ts` или `tests/<feature>.spec.ts`,
плюс всегда прогоняется полный набор (`npx vitest run`) до и после
изменения, чтобы доказать отсутствие регрессий. На момент последней
сессии — **1009 тестов, все зелёные**, 26 test-файлов.

## 5. RPG-слой: деньги, здоровье, покупки, карьера

Игрок получает деньги за пройденные уроки (`onLessonComplete` в
`life.ts`), тратит на еду (восстанавливает голод/настроение), одежду и
обувь (влияют на бонус к собеседованию `interviewBonus`), жильё, машину,
технику (бонус к XP), путешествия и «уют» (только настроение). Полный
каталог — `src/data/shop.ts`:

- `FOOD` (12 блюд), `CLOTHES` (10 предметов top/shoes),
  `ACCESSORIES` (5, один слот экипировки `Life.accessory`: часы/рюкзак/
  наушники/очки/сумка-тоут — влияют на `interviewBonus` и видны на
  фигуре персонажа), `HOMES` (7 уровней жилья), `CARS` (7 машин с
  собственной SVG-иконкой силуэта, `Car.body`), `TECH` (7 гаджетов,
  бонус к XP), `TRIPS` (7 поездок), `COMFORT` (6 вещей для настроения,
  без геймплейного бонуса, чисто мотивационные).

**Персонаж** (`src/data/avatar.ts` + `src/ui/character.ts`) — SVG,
рисуется программно (не спрайты/картинки), **в полный рост** (голова,
торс, руки, ноги, обувь), с 8 причёсками на пол, 6 цветами глаз,
5 тонами кожи, 3 стилями бороды (только у мужского персонажа), очками,
кепкой. Одежда/обувь/аксессуар на фигуре берутся **живьём** из
`Life.wear`/`Life.accessory` (экран «Жизнь» их меняет, экран «Персонаж»
их только показывает + управляет чертами лица/причёской).

**Здоровье и смерть** (см. §6) — новая механика этой сессии.

**Карьера** (`src/data/careers.ts`, `src/ui/career.ts`) — 9 вакансий от
стажёра (45k ₽) до Middle (320k ₽), каждая требует пройти целиком
конкретные акты (`reqActs`) и иногда капстоун (`reqCapstone`).
Собеседование — **диалог с тех-лидом** (см. §6): вопросы на ~60%
технические (по темам актов вакансии, банк — `interview.ts`) + ~40%
поведенческие (`SOFT_QUESTIONS`, 12 штук). Проходной балл растёт с
грейдом (0.6 → 0.8). Оффер — это флаг `Progress.jobs[jobId] = true`,
не отзывается и не «действует по времени» — коллекция достижений, а не
симуляция реальной занятости.

## 6. Что добавлено в САМОЙ ПОСЛЕДНЕЙ сессии (важно для продолжения)

Пользователь попросил одним большим запросом: диалоговые собеседования
с тех-лидом, смерть/экзамен на выживание при обнулении здоровья, более
красивого персонажа в полный рост с одеждой/аксессуарами, больше машин/
еды/путешествий/жилья/вещей для настроения, редизайн UI, файл-онбординг
(этот файл), полный прогон тестов, пентест, и CEO-стратегию развития.
Модель работы: пользователь лёг спать и заранее сказал, что ответ
«продолжай» подразумевается на любой вопрос — вся сессия шла
автономно.

Сделано (все пункты закоммичены в `vite-rewrite`, задеплоены в
`main:next/index.html`, тесты зелёные на каждом шаге):

1. **Магазин расширен**: +5 еды, +3 одежды/обуви, +2 жилья, +4 машины
   (с SVG-иконками силуэта), +3 техники, +4 поездки, **новый слот
   аксессуаров** (`ACCESSORIES`, `Life.accessory`, `BuyKind: "accessory"`,
   `unequipAccessory()`), **новая категория «Уют»** (`COMFORT`,
   `Life.comfort: string[]`, `BuyKind: "comfort"`) — вещи только для
   настроения, без геймплейного бонуса. UI: `src/ui/life.ts` получил
   вкладки «Аксессуары» и «Уют», `carIcon()` рисует силуэт машины.
2. **Персонаж — теперь в полный рост**: `avatarSVG()` в
   `src/data/avatar.ts` полностью переписана (viewBox `0 0 200 360`
   вместо `0 0 200 210`), рисует торс/руки/ноги/обувь, обувь красится по
   `Life.wear.shoes`, аксессуар рисуется оверлеем
   (`accessoryOverlay()`). Добавлено 2 причёски на пол (итого 8/8),
   2 цвета глаз (итого 6), 3 стиля бороды (`BEARDS`, `beardStyle` —
   выбирается в `ui/character.ts`, показывается только когда
   `beard=true` и `sex==="m"`).
3. **Собеседования — диалог с тех-лидом**: `runInterview()` в
   `src/ui/career.ts` рисует чат (`.iv-chat`/`.iv-msg`/`.iv-bubble`,
   CSS в `style.css`) — сообщения от именованного интервьюера
   (`INTERVIEWERS` — своё имя на каждую из 9 вакансий) и ответы
   игрока справа. Механика ответов та же (MCQ), но подача полностью
   диалоговая. Топ-3 вакансии (`polka`/`granit`/`stream`) расширили
   `reqActs` на акты 11–14 (Prometheus/Grafana/Zabbix/Python), которых
   не было, когда вакансии писались (курс тогда заканчивался на акте
   10) — теперь топовое собеседование реально спрашивает весь курс.
4. **Смерть и экзамен на выживание** — принципиально новая механика:
   `isDead(life)` в `engine/life.ts` (`health <= 0`). В `main.ts`
   функция `checkDeath()` вызывается из **каждого** `persist()` (это
   единая точка сохранения прогресса, вызывается отовсюду — из
   магазина, экрана персонажа, завершения урока) и один раз при
   старте приложения. При обнаружении смерти: `Progress.deathPending
   = true`, ввод блокируется, открывается `src/ui/revival.ts` —
   диалоговый экзамен (тот же чат-паттерн, что и у собеседований) по
   **всем пройденным на данный момент актам** (тема вопросов строится
   через `ACT_TO_TOPIC` из `careers.ts`, банк — `interview.ts`,
   до 12 вопросов, проходной балл 70%). **Сдал** — здоровье
   восстанавливается до 50, прогресс сохраняется. **Провалил** —
   `clearProgress()` + прогресс обнуляется полностью, курс начинается
   заново с урока 1.1. `Progress.deathPending` также перепроверяется
   при загрузке страницы — если игрок перезагрузил вкладку посреди
   кризиса, экзамен откроется снова, а не пропадёт.
5. **UI**: шапка навигации — служебные кнопки «как играть»/«сброс»
   визуально отделены (`.tbtn-ghost`, `.tbtn-danger`, `.sp-sep`
   разделитель) от основных игровых кнопок, чтобы не выглядеть
   равнозначными действию «пройти собеседование». **Это только первая,
   наиболее заметная часть UI-редизайна** — полный редизайн всей
   палитры/типографики/карточек за пределами этой правки **не
   выполнялся** ввиду объёма (1447 строк `style.css`); дальнейшие шаги
   расписаны в стратегическом плане, который был предоставлен
   пользователю в чате этой сессии, и ждут согласования.

Все изменения — аддитивные (новые опциональные поля, новые файлы, новые
CSS-классы), ни один существующий тест не изменил смысл без явной
причины (только тесты `tests/avatar.spec.ts` намеренно обновлены под
новый `viewBox` и новый путь бороды — это ожидаемое изменение
визуального контракта, а не регрессия).

## 7. Капстоун — единственное «настоящее» окружение

`src/sandbox/capstone.ts` открывает `@xterm/xterm` и подключается по
WebSocket к `sandbox-server/server.js` (Express + `ws` + `node-pty`).
Модель безопасности сервера (см. комментарий в начале файла): один
Docker-контейнер на пользователя, `--network none`, `--cap-drop ALL`,
`--read-only` + tmpfs, non-root, лимиты memory/cpu/pids, таймаут сессии,
rate-limit по IP, проверка Origin. Открывается только если в сборке
задан `VITE_SANDBOX_URL` — иначе показывается заглушка со ссылками на
внешние песочницы (Killercoda, Play with Docker). Прохождение капстоуна
отмечается **вручную** самим игроком (кнопка «Я выполнил все
задания») — сервер не может автоматически проверить произвольные
задания вроде код-ревью.

## 8. Деплой — ветки и «зеркала»

Это нестандартная, но обязательная к пониманию схема:

- **`vite-rewrite`** — рабочая ветка, всё разработческое здесь.
  Источник правды.
- **`main`** — ветка репозитория GitHub Pages. Корень (`index.html`) —
  это **старая** версия игры (`src/missions`), её не трогаем.
  `main:next/index.html` — это вручную обновляемая **копия**
  собранного `vite-rewrite:play/index.html` (файл `play/index.html` в
  `vite-rewrite` — это git-committed результат
  `npm run build:single`). Автоматического деплоя из `vite-rewrite` в
  `main` нет — `.github/workflows/deploy.yml` на `main` только
  проверяет (check-only), не пушит.

**Стандартный цикл после любого изменения игры:**
```bash
# на vite-rewrite
npm test && npm run typecheck && npm run lint
npx vite build --mode single
cp dist-single/index.html play/index.html
git add -A && git commit -m "..." && git push origin vite-rewrite

git checkout main

git add next/index.html && git commit -m "deploy: ..." && git push origin main

```

## 9. История: как курс дошёл до 14×20 уроков

Изначально курс был компактнее; в двух больших сессиях (эта и
предыдущая) каждый акт был расширен на 5–10 дополнительных уроков с
нарастающей сложностью, привязанных к сюжету и подкреплённых реальными
новыми механизмами движка (не просто текстом): позиционные аргументы
bash-скриптов и `set -e`, `test`/`[ ]`, HTTP-моки для `curl`, `git
--amend`/конфликты/теги, размер Docker-образов и `-e`/`-v`, approval-
gate и rollback в CI, `terraform taint`/`state rm` и дрейф, Pending-поды
Kubernetes при нехватке ёмкости, PromQL-функции `sum(rate())`/
`histogram_quantile`, триггеры Zabbix (`zabbix trigger add/list`,
`zabbix problems`), и в Python — `os.environ`/`os.getenv` (использует
тот же `World.env`, что и bash в Акте 1 — намеренная связь) и retry-цикл
вокруг `requests`. Если тебя попросят «расширить акт N» — смотри на этот
список как на образец: **сначала небольшое расширение движка,
подкреплённое отдельным тестом, потом уроки, которые реально его
используют**, а не просто текст без интерактива.

## 10. Известные ограничения и куда смотреть дальше

Честно, без приукрашивания (это не жалобы, а карта для продолжения):

- **UI-редизайн не завершён.** Сделана только шапка навигации.
  `style.css` (1447 строк) — рабочий, но не пересмотрен целиком как
  единая дизайн-система (нет чёткой шкалы отступов/типографики,
  карточки в разных экранах оформлены слегка по-разному). Это
  наибольший оставшийся пункт из исходного запроса пользователя.
- **Здоровье было декоративным до этой сессии** — единственный способ
  сейчас его уронить до нуля — это долгий голод при частом прохождении
  уроков (`onLessonComplete`: `-3` здоровья при `hunger < 10` после
  урока) или ручная правка `localStorage` (как в тестах). В реальной
  игровой сессии дойти до смерти небыстро — это нормально для обучающей
  игры, но если хочется, чтобы смерть ощущалась чаще/реже, крути
  константы в `onLessonComplete`/`eat` в `engine/life.ts`.
- **Карьера — не симуляция занятости.** Оффер — это ачивка, а не
  «текущее место работы» с зарплатой, которая реально прилетает
  каждый месяц. `job.pay` — это просто текст. Если нужно превратить
  найм в реальный источник дохода — потребуется новое понятие «текущая
  работа» отдельно от «полученных офферов».
- **`src/missions/*`** (старая версия) существует только для миграции
  сохранений — не расширяй её.
- **Комментарии к миссиям** — в `supabase_schema.sql` есть таблица
  `comments` с RLS-политиками, но в коде (`src/ui/*`) нет ни одного
  экрана, который её использует. Мёртвая, неиспользуемая часть схемы —
  либо реализовать, либо удалить из схемы при следующей ревизии БД.
- **Пентест-находки не исправлены** — это сознательное решение: находки
  зафиксированы (переданы пользователю в чате этой сессии; ключевая —
  `sandbox-server/server.js` проверяет `Origin` только когда заголовок
  присутствует, отсутствующий `Origin` целиком обходит allowlist), но
  не были ещё исправлены и не согласованы с пользователем как
  приоритет.

## 11. Как продолжать работу с этим файлом

- Если тебя попросили что-то небольшое — просто делай, следуя
  паттернам выше. Дисциплина «сначала факты, потом правка» — хорошая
  инженерная гигиена независимо от того, форсирует её инструментарий
  или нет.
- Если тебя попросили расширить акт/добавить контента — см. §9, это
  устоявшийся, проверенный рабочий процесс.
- Если тебя попросили что-то в UI — сохраняй паттерн «функция рисует
  строку innerHTML и перепривязывает onclick», не вноси частичный
  React/шаблонизатор.
- Всегда: `npm test` (должно быть 1000+ зелёных), `npm run typecheck`,
  `npm run lint` перед коммитом. Всегда деплой по циклу из §8, если
  просили «чтобы это было видно/поиграть».
- Не добавляй строки атрибуции в коммиты/PR, если явно не попросили —
  это стоячее указание пользователя из предыдущей сессии, вероятно
  сохраняющееся и дальше.
